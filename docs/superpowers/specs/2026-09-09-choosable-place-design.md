# A choosable place in South Tyrol

Design, 2026-09-09. Supersedes the fixed location in `domain/DorfTirol.kt`.

## The problem

Every screen in the app is about Dorf Tirol, and the location is a set of constants: an ISTAT code
for the SIAG municipality forecast, a latitude and longitude for Open-Meteo and GeoSphere, a district
id for the bulletin, and a station code for the live observation. Nothing about the architecture
needs those to be constants — they thread through the repository as parameters already, or would if
they were passed rather than read from an object. What is missing is a way to choose them, a place to
keep the choice, and a catalogue of what may be chosen.

South Tyrol is the natural boundary and not an arbitrary one: SIAG KMOS is addressed by the ISTAT
code of a South Tyrolean municipality, the bulletin is published per South Tyrolean district, and the
live stations are the province's own network. Outside the province three of the seven sources simply
have nothing to say.

## What was decided

Four questions were put and answered before this was written.

**One place at a time, switchable.** Not several places to swipe between. The cache stays one set of
rows per place rather than a fan-out, and the widget, the notifications and the background worker
have no ambiguity to resolve — they mean the current place, because there is only one.

**The bulletin follows the place, through a bundled municipality-to-district table.** No API exposes
which of the seven weather districts a municipality belongs to: `Region` on the ODH municipality
record is a tourism region with no name, and `TourismVereinIds` on the district record is null. The
alternative — a second setting for the district — was rejected because two knobs can disagree
silently, and someone in Bruneck reading the Vinschgau bulletin would have no way to notice.

**The picker opens from the place name on the hero.** It is already the first line on the screen;
making it the button adds no chrome. The settings sheet gets a row to the same screen so it is
discoverable both ways.

**The cache keeps the last three places.** Wiping on every switch was rejected: it contradicts the
rule this app already holds to, that the UI renders whatever is cached, and it would leave an offline
switch showing nothing at all. Keeping every place ever opened was rejected as unbounded — roughly
1–2 MB each, so a curious reader browsing all 116 would carry a couple of hundred megabytes.

## What a place is

`domain/Place.kt`:

```kotlin
@Serializable
data class Place(
    /** The six-digit ISTAT code SIAG KMOS is addressed by, e.g. "021101". */
    val istat: String,
    val nameDe: String,
    val nameIt: String,
    val nameEn: String,
    val lat: Double,
    val lon: Double,
    val altitudeM: Int,
    /** 1..7, which of the seven weather districts publishes this place's bulletin. */
    val district: Int,
    /** The nearest station, or null where none is close enough to speak for this place. */
    val station: NearbyStation?,
)

@Serializable
data class NearbyStation(
    val code: String,
    val name: String,
    val lat: Double,
    val lon: Double,
    val altitudeM: Int,
    val distanceKm: Double,
)
```

`DorfTirol.kt` becomes `SouthTyrol.kt` and keeps only what is genuinely province-wide: `ZONE`
(`Europe/Rome`), MeteoAlarm's `REGION` (`IT002`), and `DEFAULT_ISTAT` (`021101`, Dorf Tirol, so an
existing installation opens on the place it has always shown).

The display name is chosen by the reader's language, through the same `Formats`/locale the rest of
the app already resolves — never by the JVM default.

## The catalogue

`app/src/main/assets/places.json`, about 25 kB, all 116 municipalities. Generated by
`tools/generate-places.py` and checked in, on the same terms as the recorded fixtures: regenerated
deliberately, reviewed before committing, never fetched at runtime.

The generator combines three sources:

- **ODH `/v1/Municipality`** — `IstatNumber`, `Latitude`, `Longitude`, `Altitude`. One request, all
  116. Its `Detail` titles are not used: they are German-only and inconsistent (Dorf Tirol appears as
  "Tirol").
- **SIAG KMOS, once per ISTAT code** — `nameDe`, `nameIt` and `nameEn`. It also returns `nameRm`,
  which is dropped: Ladin is not one of the app's three languages. This is also the liveness
  check: a code that does not return a `temp3` series does not belong in the catalogue.
  Sampling eight municipalities at random on 2026-09-09 returned a full 47-point series and correct
  German and Italian names for every one.
- **SIAG `/api/v2/station`** — the nearest station to each municipality, by great-circle distance,
  subject to the cap below.

Precomputing the station is not only a convenience. `StationDownscale` needs the models' temperature
*at the station*, which means an Open-Meteo call at the station's own coordinates and altitude. If
the station were resolved at runtime from the live station list, that call would have to wait for the
station response; precomputed, it goes out in parallel with the other six.

The generator is run by hand, not in CI. Its output is reviewed as data, and the review that matters
is the district column.

### The district table

The one datum no upstream provides. The generator reads it from a table keyed by ISTAT code,
maintained in the generator itself, and every one of the 116 entries must be present — a missing
entry fails the generation rather than defaulting to a district.

The seven districts, as the API names them:

| Id | Name (de) |
|----|-----------|
| 1 | Bozen, Überetsch und Unterland |
| 2 | Burggrafenamt – Meran und Umgebung |
| 3 | Vinschgau |
| 4 | Eisacktal und Sarntal |
| 5 | Wipptal – Sterzing und Umgebung |
| 6 | Pustertal |
| 7 | Ladinien – Dolomiten |

A wrong entry shows the wrong valley's bulletin, silently and plausibly. This table gets a human
review before the catalogue is committed.

## How the choice threads through

`AppSettings` gains `placeIstat: String`, defaulting to `SouthTyrol.DEFAULT_ISTAT`, stored in the
existing settings DataStore.

`PlaceCatalogue` (`data/PlaceCatalogue.kt`, `@Singleton`) parses the asset once, off the main thread,
and exposes `all`, `byIstat(istat)`, and `search(query, locale)`. An unknown or corrupt stored code
resolves to the default rather than to nothing.

`WeatherStateHolder` resolves the selected `Place` and re-subscribes to the repository when the code
changes — the same `distinctUntilChanged().flatMapLatest {}` it already uses for the bulletin
language, so the seven models are still blended once per change rather than once per screen. Home,
Sky, Compare and the bulletin all map off the holder and follow without changes of their own.

## Cache

Room schema version 4. `place` is added to `source_forecast` (primary key becomes place + source),
`observation`, `station_reference` and `refresh_meta`. `bulletin` is keyed by **district** and
language, not by place, because a district's bulletin is the same document for every municipality in
it. `warnings` stays a single row: MeteoAlarm publishes for the whole region.

The database is `fallbackToDestructiveMigration(dropAllTables = true)` and every row in it is a cache
of something fetchable, so the version bump drops and refills rather than migrating.

**Eviction.** A `recentPlaces` list of ISTAT codes, most recent first, lives in the settings
DataStore. After each successful refresh, rows whose place is not among the first three are deleted;
bulletins, being keyed by district, are evicted by the districts those three places belong to, so two
retained places in one district keep one bulletin between them. Three is a judgement, not a
measurement: it covers home, work and one more.

## Refresh

`WeatherRepository.snapshot(place, language)` and `refresh(place, language)`. Each upstream takes
what it needs from the place:

| Source | Keyed by |
|--------|----------|
| Open-Meteo, five models | `lat`, `lon` |
| Open-Meteo station reference | `station.lat`, `station.lon`, `station.altitudeM` |
| GeoSphere AROME | `lat`, `lon` |
| SIAG KMOS | `istat` |
| Bulletin | `district`, language |
| Live station | `station.code` |
| MeteoAlarm | nothing — the region |

The background worker refreshes the current place only. A place left behind goes stale and says so
when it is returned to, which is the behaviour the app already has for a failed source.

## Station

The nearest station within **20 km**. Beyond that the reading is not about this place any more, in a
province where 20 km can cross a ridge, so `station` is null and the app says less rather than
something wrong: no measurements card, no downscaling, and the hero falls back to the consensus —
which is already at the right altitude for the place.

Two runtime guards on the precomputed choice:

- If the precomputed code is absent from the live station response — a station decommissioned since
  the catalogue was generated — fall back to the nearest station in that response, and skip the
  downscaling for that refresh, since the reference call went out for the wrong coordinates.
- If neither is available, the place behaves as one with no station.

`StationDownscale` needs no logic change. Its inputs move from constants to the place, and its
existing guards — a maximum plausible correction, a maximum reference age — keep doing their work.

## Interface

**The hero.** The place name gains a chevron and becomes a button. Tapping it opens the picker.

**The picker** is a route, not a bottom sheet: 116 rows plus a search field deserve a back-stack
entry and a proper back gesture. It is not a bottom-bar destination, so it is reached with a plain
`navigate`, not `openTopLevel` — the one-way-in rule guards the three bottom-bar routes and does not
apply here. Each row shows the name, the altitude, and the district; the current place is checked;
choosing one pops back to where the reader came from.

Search matches all three names, case- and diacritics-insensitively, so "meran" finds both Meran and
Merano and "gais" finds Gais.

**The settings sheet** gains a place row at the top, opening the same screen.

**Widget and notifications** take the place name. The widget already updates after every refresh, so
it follows a change without new plumbing.

Strings for the picker go into `values`, `values-it` and `values-en`. District names are not
translated here — they arrive localized from the API.

## Testing

Catalogue, on the JVM: 116 entries; ISTAT codes unique and six digits; district in 1..7 for every
entry; a non-empty name in all three languages; altitudes within the province's range; every station,
where present, within the cap.

Search, on the JVM: all three languages, case, diacritics, and a query matching nothing.

Repository, on the JVM against fixtures: two places do not bleed into each other's rows; a refresh of
one leaves the other's cache intact; eviction keeps three and drops the fourth; the bulletin is shared
by two places in the same district and not by two in different ones.

`HomeStateBuilder`, on the JVM: a place with no station shows the consensus and no measurements card,
and reports no adjustment.

On the device: the picker renders, search filters, choosing a place changes the home screen, and the
back gesture returns without changing anything.

A second recorded fixture — Sterzing: a different district, a more distant station, and a genuinely
different forecast — so the tests exercise a place that is not the default.

## Non-goals

- **No GPS or current location.** The app covers one province; a location permission would buy a
  guess at which municipality the reader is in, at the cost of a permission prompt.
- **Nothing outside South Tyrol.** KMOS, the bulletin and the station network stop at the border.
- **No per-widget place.** One place, one widget content.

## Risks

The district table is hand-made and everything else is generated or fetched. A wrong entry is
invisible: a plausible bulletin for the wrong valley. It is reviewed once, and the review is the
gate on committing the catalogue.

A second risk worth naming: places at the edge of the province, or high on a ridge, may have a
nearest station that is close in kilometres but far in metres. The downscaling corrects for altitude
using the models' own difference between the two points, so this is handled — but where the
correction comes out implausibly large it is refused, and such a place shows the consensus instead.
That is the intended behaviour, not a gap.
